The **Background Worker** (`apps/worker`) is EmitMail's asynchronous delivery engine. By decoupling mail dispatch from the HTTP API, EmitMail can handle massive email dispatch volume without blocking API response times or exposing mail transmission timeouts to client applications.

---

## 2. Decoupled Delivery Architecture

```text
Client API Request
       │
       ▼
apps/api (Port 4000)
       │ (Enqueues job in < 15ms)
       ▼
Redis BullMQ Queue ('email-delivery-queue')
       │
       ▼
apps/worker (Concurrent Workers)
       │
       ├─► 1. Lookup Domain & Decrypt 2048-bit RSA DKIM Private Key
       ├─► 2. Query Recipient Domain MX Records (e.g. gmail-smtp-in.l.google.com)
       ├─► 3. Establish Direct TLS Handshake to MX on Port 25
       ├─► 4. Transmit with EHLO mail.yourdomain.com & Return-Path bounces@send.<domain>
       └─► 5. Update PostgreSQL status to DELIVERED or schedule BullMQ exponential retry
```

## 3. Direct MX Resolution & SMTP Transport

EmitMail transmits email directly from your server's IP address to recipient destination MTAs (Google Workspace, Microsoft 365, ProtonMail) without relying on third-party relay intermediaries.

### MX Resolution Workflow
When an outbound email job is picked up by `emailDelivery.worker.ts`:
1. Extract recipient domain (e.g. `user@gmail.com` -> `gmail.com`).
2. Query DNS for `MX` records ordered by priority:
   ```typescript
   const mxRecords = await dns.promises.resolveMx(domain);
   const primaryMta = mxRecords.sort((a, b) => a.priority - b.priority)[0].exchange;
   ```
3. Initialize a direct Nodemailer SMTP transport pointing to `primaryMta:25`.

### 2048-Bit DKIM Signing
The worker decrypts the domain's 2048-bit RSA private key using `ENCRYPTION_KEY` and injects cryptographic signatures into every outbound MIME envelope:

```typescript
const transport = nodemailer.createTransport({
  host: primaryMta,
  port: 25,
  secure: false,
  dkim: {
    domainName: domain.name,
    keySelector: domain.dkimSelector || 'esp',
    privateKey: decryptedPrivateKey,
  },
  name: env.SMTP_EHLO_HOSTNAME, // e.g. mail.yourdomain.com
});
```

## 4. Inbound Email Worker & Webhooks

When incoming emails are captured by the Inbound SMTP receiver on port 2525, they are queued to `inbound-email-queue`:

- `inboundEmail.worker.ts` parses headers, extracts spam indicators, and stores parsed HTML in `InboundEmail`.
- If your account has active webhooks subscribed to `inbound.email.received` or delivery lifecycle events (`email.sent`, `email.delivered`, `email.bounced`), `webhookDispatcher.service.ts` sends an HTTP POST with an `X-EmitMail-Signature` header calculated using HMAC-SHA256:

```typescript
const signature = crypto
  .createHmac('sha256', webhookSecret)
  .update(JSON.stringify(payload))
  .digest('hex');
```

## 5. Concurrency & Performance Tuning

Worker concurrency is controlled via environment variables:
```bash
# Number of parallel email delivery jobs processed per worker process
WORKER_CONCURRENCY=10
```

When running in production under heavy volume, you can scale workers horizontally by deploying multiple instances of `emitmail-worker` connected to the same Redis cluster without changing the API server.
